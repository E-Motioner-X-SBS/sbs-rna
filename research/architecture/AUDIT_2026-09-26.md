# Audit, 2026-09-26

Same hunt, same class: **a component that exists, is measured, and whose output
is never checked for basic validity.** Sixteen findings, all in the
monitoring and supervision layer rather than the model. Two of them are the same literal
string, `pretrain_small.pt`, written into two files and stale in both from the
moment the run moved to `shared400` — and in each file a different guard
turned the staleness into silence rather than an error. Everything below is pinned in
`scripts/sampling/verify_claims.py` or in `src/pharos/data/test_dataset.py`.

Training was stopped at step 13,750 on 2026-09-25 and the scheduler is held, so
none of this was found by watching a run. It was found by asking, of each
number that gets quoted, *where does this come from and when was it last
actually computed.*

### Why 20 matters beyond the count

Head 9, one block above it in the same function, gets this right: *"Unannotated
pairs are excluded by the mask rather than given a class: not-a-base-pair is
not a kind of base pair."* Head 10 is the same sentence about loops, and it was
never written. The consequence is directional, not just noisy — class 0 is the
majority class, so the unfounded labels all push the same way:

| | class 0 (no loop) | class 1 (hairpin) | class 2 (internal) |
|---|---|---|---|
| as trained | **74.4%** | 7.3% | 18.3% |
| on chains where the label means something | **64.4%** | 10.1% | 25.5% |

74.4% was also head 10's reported majority baseline, so a head that learned
nothing but "predict 0" was being scored against a bar that 28.2% of its own
training data had raised for it. Measured through the real batch path after the
fix: `loop_mask` covers 82.9% of residues instead of 100%, and the class shares
land at 63.7 / 10.3 / 25.9.

against `log 512 = 6.238` nats:

|---|---|---|---|

### The telemetry defect is now impossible to repeat quietly

`csv.DictWriter(extrasaction="ignore")` is the right behaviour for a writer —
a stray key must not kill a training run at hour nine — and the wrong
behaviour for a codebase, because the caller's author gets no signal. Both
instances of this defect were found by reading a csv header, which is not a
method that scales. `RunLog.log` now prints one line per undeclared key per
run:

```
[telemetry] stage5_3d: 31 column(s) passed to log() but not declared,
so they are NOT being written: part_balance, part_base, ...
```

It still writes the row. It just stops being silent about what it left out.

### The worst one, and the two fixes that caught it

Finding 32 is the only one today where a wrong number was actually produced,
written to disk, and would have been quoted. It is also the clearest case of
the pattern, because every individual piece was correct:

- redrawing the split family-disjoint was a deliberate improvement;
- `Pharos3DDataset(DATA, split="test")` does exactly what it says;
- `measure_cascade_recall.py` loads the scorer and measures recall correctly;
- the scheduler re-runs it every 24 hours, as intended.

What was missing is that a model and an evaluation have to agree on *which
draw of the split they mean*, and nothing recorded it on either side. So the
composition of the answer was wrong while every part of it was right.

Two of today's earlier fixes are what surfaced it. Finding 19 made a failing
GPU task raise a problem instead of printing `FAILED` into a log, and finding
22 made the watcher report what it is actually looking at — which is how a
cron tick at 23:34 came to leave evidence worth reading at all. The guard now
composes the other way too: the re-measurement exits 1, and that exit is now
visible instead of swallowed.

Note what the numbers would have looked like. Contamination inflates; the new
test split is 94% short chains and cascade recall is strongly length-dependent,
which deflates. The aggregate moved 0.264 → 0.2115 — *down*, in the direction
that reads as an honest regression. A plausible number moving the plausible way
is what makes this class of defect expensive.

**And it is not one file.** Every pinned model result in the repository was
measured under the old draw, because the re-draw postdates every checkpoint:

| result file | its test split | corpus now |
|---|---|---|
| `block_scorer_results.json` | 1,450 | 4,081 |
| `block_scorer_results_small.json` | 1,450 | 4,081 |
| `pharos_small_results.json` | 1,358 | 3,993 after stage-5 filters |
| `pharos_small_results_randinit.json` | 1,358 | 3,993 |

Those numbers are **valid for the split they were measured on** and are not
being retracted. What is now recorded, rather than assumed, is that they are
not measurements of the current corpus, and that re-measuring any of them
requires retraining the model under this draw — scoring the existing
checkpoints on today's test set is the contamination above, not an update.
`verify_claims.py` prints the inventory as a warning every run.

### The scheduler was suppressing itself

Finding 31 is the one with teeth, because it is the only one that could have
stopped training rather than merely mis-described it. `do_gpu_work` starts
nothing when `training_alive()` is true, and `training_alive()` was true
whenever any process on the machine had a trainer's file name in its command
line. The watcher runs `verify_claims.py` at the top of every tick, and
`verify_claims.py` runs `--help` on all six trainers. The window is short and
the tick is 30 minutes, so this would have fired occasionally, skipped a
resume, and left behind one line in a log saying training was already running.

It is checked behaviourally now rather than by reading the source: the guard
starts a process whose argv contains `scripts/train_pharos.py`, confirms the
old predicate matches it, and requires the new one not to.

### The one that is still live

Finding 27 is not a defect that has already fired — it is one that is about to.
`mars_to_parquet.py` is running now with a four-hour timeout. When it finishes,
the held-out digest moves off `7c207664`, and the next reading of the curve
will not belong to the seven readings already in the file. That is now
**stated** in three places rather than discovered later:

- the trainer prints `held-out shard set unchanged (7c207664)` on resume, or a
  four-line warning if it has moved;
- the evaluation csv carries the digest per row, so two numbers are known to
  be comparable or known not to be;
- `verify_claims.py` fails if one csv splices two digests, and warns when the
  corpus has grown past the recorded one.

What it does **not** do is pick for you. Freezing the reserved set would keep
the curve comparable and let the held-out shards fall behind the corpus;
letting it move keeps the evaluation representative and restarts the curve.
That is a judgement about what the number is for, and it is recorded here
rather than decided quietly in a sort order.

## Finding 33 — coordinates stored as float16 in the raw crystal frame

Asked a plain question of the corpus -- do we have backbone information --
and the answer is yes, with one defect in how it is stored.

`pharos3d` carries `coords (N, 3, 3) float16` and `coord_mask (N, 3) bool`:
phosphate, C4', glycosidic nitrogen, per residue, over 13,172,991 residues in
16,604 chains. Coverage is 99.94% / 99.55% / 99.33% and 16,602 of 16,604
chains carry some coordinate. The geometry is right: C4'-N measures a median
**3.378 A** against the reference 3.38, P-P **5.884** against 6.01, C4'-C4'
**6.132** against 6.0.

What nothing checked is the **frame** those floats are written in. They are
the deposition's own coordinates, uncentred, so the median |coord| is
**170 A** and the maximum **1310 A**. float16 spacing is not uniform: it is
0.0312 A at 32 A, 0.125 A at 128 A, 0.25 A at 256 A, 1.0 A at 1024. 71% of
stored coordinates sit beyond 128 A and 22% beyond 256 A, so most of this
corpus is quantised more coarsely than the precision the numbers imply.

The damage is measurable without the original float32, because C4'-N is a
near-rigid bond whose spread is almost pure noise. Binned by |coord|, robust
sd of that bond:

| \|coord\| (A) | n | median | robust sd | fp16 spacing |
|---|---|---|---|---|
| 0-32 | 70,064 | 3.379 | 0.0790 | 0.0010 |
| 32-64 | 310,236 | 3.375 | 0.0729 | 0.0312 |
| 64-128 | 1,080,503 | 3.376 | 0.0696 | 0.0625 |
| 128-256 | 1,842,261 | 3.380 | 0.0792 | 0.1250 |
| 256-512 | 628,302 | 3.387 | **0.1148** | 0.2500 |
| 512-2048 | 36,247 | 3.391 | **0.1636** | 0.5000 |

Flat at ~0.07 A -- real crystallographic variation -- until the fp16 spacing
overtakes it, then it doubles. That is the quantisation, visible directly.

**Why it survived.** Every check that could have caught it is translation
invariant. `DiffusionStructureHead.loss` centres through `random_rigid`, so
training never sees the offset; the bond-violation term reads differences,
which are unaffected by where the origin is; and the medians above are
correct precisely because quantisation is unbiased. The corpus looks healthy
from every angle except the one nobody took, which is the class this audit
keeps finding: measured, plausible, never checked for the thing that was
actually wrong.

**Cost and fix.** It is label noise on head 3's only supervision, ~0.10-0.16 A
where good backbone prediction is a 1-2 A problem. Centring each chain before
the float16 cast drops max |coord| from 1310 A to 169 and the median from 170
to 49, putting the whole corpus at <=0.125 A spacing and most of it at 0.031.
Centring at load time cannot recover it -- the precision is gone at write.
The structure head is translation invariant anyway, so nothing downstream
depends on the absolute frame being kept.

**Fixed, and the corpus rebuilt.** Centring happens in `build_entry` before
the float16 cast, over **resolved atoms only** -- the first version of the
measurement averaged the unresolved (0, 0, 0) slots in too, which dragged the
centroid tens of Angstroms off the chain and made centring look *worse* than
leaving it alone (0.1143 against 0.1044). That near-miss is worth keeping:
the fix had a bug that the fix's own metric reported as a negative result.

Corpus-wide, over all 13,172,991 residues:

| | max \|coord\| | median \|coord\| | C4'-N spread |
|---|---|---|---|
| before | 1310.0 A | 236.1 A | 0.0853 A |
| after | 202.0 A | 50.0 A | **0.0556 A** |

float32, the parser's own precision, gives 0.0511. No residue is left beyond
256 A. The bond median also moved 3.3866 -> 3.3819 against a 3.38 reference:
quantisation at that magnitude was biasing the bond, not just broadening it.

`coord_center` (float32, per chain) is written to every shard and into the
manifest, so `coords + coord_center` is the deposition frame again --
round-trip verified at 0.0312 A, half a float16 ULP.

**The split is bit-identical**: digest `3900e076` before and after, 16,604
chains, 13,172,991 residues, 63,298,800 contacts all unchanged. Nothing
measured against this corpus needs re-measuring; only the coordinates moved.
The old one is kept as `pharos3d_v3_uncentred`.

Two checks now exist where none did. `build_dataset.py` reads its own shards
back and refuses to ship a corpus whose max |coord| exceeds 256 A, whose
glycosidic bond is off reference, or whose bond spread exceeds 0.075 A, and
pins the numbers in `manifest["geometry"]`. `test_dataset.py` property 9
asserts the same three things plus the presence of `coord_center`; it fails
on the old corpus, which is the only evidence that it tests anything.

Asking the same question of the corpus' other float16 arrays -- is the
magnitude small enough that relative precision still holds -- turned up

It is a thin tail: p99 is 3.59 and p99.9 is 6.49, and only 77 of 15,852

## Findings 34-37 — a full re-audit of the architecture

All sixteen test modules passed before this pass and all seventeen pass
after, `verify_claims.py` reproduces every claim, and `audit_head_outputs.py`
flags nothing. That is the point: four of these were live the whole time.

### 34. Nothing stopped a NaN

No trainer checked whether its loss was finite. `nan.backward()` runs,
`clip_grad_norm_` passes NaN through, `opt.step()` writes NaN into every
weight, the checkpoint at the next `ckpt_every` boundary saves it, and the
run continues for days producing a file that cannot be resumed from.

The held-out monitor could not see it either, and this is the sharper half.
`float("nan")` parses without complaint, and **every comparison against NaN
is False** -- so `bits >= UNIGRAM_BITS` was False, the reading was taken as
better than unigram, the no-progress check compared NaN deltas (also False),
and the verdict was **OK**. The monitor whose entire job is to notice a run
going wrong was structurally unable to notice the most obvious way one does.

Fixed both ends. `pharos.train.guard.check_loss` raises before the optimiser
and names which head went non-finite first, because the heads are summed and
the sum only records that something broke; all four trainers call it. The
monitor's `f()` now rejects non-finite as unreadable, which routes a NaN to
the existing ALERT. `src/pharos/train/test_guard.py` pins both, including
that the guard is called *before* `backward()` and not after.

| output | state |

`disorder_logit` is the one worth dwelling on: the data was extracted,

The phantom `fitness` weight is removed, the docstrings now say which heads
are and are not trained, and `test_pharos.py` property 7c pins the whole
emitted surface as three explicit sets -- 11 trained, 3 trained indirectly,
4 untrained with a stated reason each. A new head fails that test until
someone classifies it.

The first version of 7c discovered the sets by searching the trainers for
`out["key"]` and reported `fitness` as trained -- because the comment saying
there is no `out["fitness"]` anywhere contains the string `out["fitness"]`.
A check that greps its own prose, committed inside the thing built to catch
checks that cannot see. It is now a pinned list.

### 36. `PharosHeads.loss` was dead code that disagreed with the trainers

A static method summing every head under a documented weight table --
contact 1.0, distance 1.0, ss 0.5, mg 0.3, rigidity 0.3, reactivity 0.5,
base 0.2, fitness 0.5, splice 0.5, coords 1.0. **Called by nothing**: not the
trainers, not a test. The real stage-5 weights are assembled inline and are
not those; `distance` is 0.5 in the trainer against 1.0 here, and this table
is the one a reader finds first.

It also held the project's only non-finite guard, on a path no gradient ever
took, while the four trainers that do take gradients had none -- finding 34.
Deleted rather than wired up: two loss definitions is how they drift, this

## Stage 6 — the fitness head, wired, and what wiring it found

Stage 6 was the last of the four untrained heads with data already on disk
(finding 35). It is now implemented: `build_fitness_dataset.py` builds the
corpus, `train_sequence_stages.py` co-trains the head beside stages 2 and 3
at weight 0.3, and `eval_fitness_zeroshot.py` scores the benchmark the
corpus holds back. Four defects turned up on the way, all of the class this
audit keeps finding — a thing that is measured, is finite, is numeric, and is
not what it is named.

### 38. The two fitness benchmarks are largely one dataset

`data/benchmarks/fitness/` holds NABench (47 assays) and RNAGym (70). They
look like two corpora. **24 of the 31 assays on the RNAGym ncRNA leaderboard
are also shipped by NABench**, usually under the same file name. Training a
fitness head on "NABench" and reporting its score on "RNAGym" would be
reporting a score on its own training data, and nothing in either benchmark's
own tooling would say so. The same shape as finding 32, one corpus over.

Worse, the overlap is invisible to either obvious check on its own:

* **by sequence alone it looks disjoint.** NABench keeps the full construct
  (T7 promoter, primer sites) and RNAGym trims to the core, so
  `Guy_2014_tRNA` is 132 nt in one and 105 in the other and the two files
  share **zero** exact sequences. Same experiment, same variants, different
  flanks and therefore different mutation numbering.
* **by name alone it looks disjoint.** `Beck_2022_ribozyme` and
  `Roberts_2023_cepeb3_ribozyme` are **21,321 identical sequences** under two
  unrelated names, correlating at Spearman 0.985. So are
  `Rachapun_2022_L1_R1_R2_ribozyme` and `Rachapun_2022_f1u_R1_R2_ribozyme`,
  which are byte-identical.

The builder therefore defines the benchmark first, holds back all 31
leaderboard assays, and checks the training set against it **twice** — once
by assay identity and once by exact sequence — refusing to write a corpus
rather than reporting a leak. `verify_claims.py` re-derives both from the
written files, and `test_fitness.py` pins them with the two failure modes
above written down beside the assertions.

### 39. A column called `DMS_score` that is a read count

`Roberts_2023_HDV_ribozyme` is shipped by both sources. The two copies hold
the **same 33,930 sequences** and their scores correlate at **Spearman
0.0056** — uncorrelated. NABench's column is integers from 4 to 438,152 with
a median of 45: a sequencing read count, which is dominated by depth.
RNAGym's is a normalised activity in [0, 1.6].

Nothing about the NABench column is malformed. It is numeric, finite,
complete, correctly typed and named `DMS_score`. A loader that read it would
train a fitness head on library size. It was found by correlating the two
sources against each other rather than by validating either one, which is the
only way it could have been found: a single copy of that column passes every
check you would think to write.

Found with it: `Gregory_2018_mRNA`, where **all 287** sequences contain a
literal `X`. Both are excluded by name with the reason recorded in the
manifest, and `test_fitness.py` asserts every NABench file on disk is either
in the benchmark, in the training set, or excluded with a stated reason — so
a new file cannot be quietly ignored.

### 40. The consensus wild type is the wrong wild type for 9 of 31 assays

The masked-marginal convention needs each assay's wild type: it is the
sequence whose mutated positions get masked. The obvious way to get one
without trusting a metadata file is the per-column majority base over the
variants. That reconstructs every variant exactly for 22 of the 31 assays and
**fails for 9** — `Kobori_2018_ribozyme` scores 1,023 of 16,383.

The reason is structural: those assays are *complete randomisations* of a
small position set. `Kobori_2018` is 4^7 − 1 variants over 7 positions, so at
each randomised position every base appears equally often and the majority
base is a coin toss. There is no consensus to find.

A scorer built on the consensus would not have raised. It would have read a
real log-probability at a position that is not the mutated one and reported a
number for all 31 assays. RNAGym's own reference baselines print `[SKIP]` and
return `NaN` in the equivalent case, which averages away.

So the builder takes `RAW_CONSTRUCT_SEQ` from the reference sheet **and then
checks it**: every variant must equal the wild type with its listed mutations
applied. All 31 reconstruct at 100%, the per-assay counts are pinned in the
manifest, and an assay that fails is refused rather than benchmarked.

### 41. Two of the three streams in stages 2-3 were starving, and the file said the opposite

`train_sequence_stages.py` created one generator per stage per epoch and
stopped pulling from a stage once its generator raised `StopIteration`. With
342 secondary-structure batches against 10,488 probing batches, **head 4
received a gradient on 3.3% of the steps in an epoch** and then sat idle.

The file claimed the reverse, twice. Its docstring justified
`STAGE_WEIGHTS["ss"] = 0.5` by saying 2D "dominates the gradient by virtue of
being read more often per epoch", and the comment above the validation split
said "10,934 secondary-structure examples are recycled about 31 times for
every pass over Ribonanza's 335,616 profiles. Overfitting is the expected
outcome of that ratio." Neither was true: no generator was ever recreated, so
nothing was recycled at all, and the weight was holding back the channel that
was starving.

Neither number was wrong by a typo. Both describe the loop the author
intended — one batch from each stage, every step — and `estimate_steps` has
always computed `max` of the stream lengths, which is the epoch length that
loop would have. Only the loop itself disagreed, and it had never run, so
nothing could notice.

Every stream now restarts inside the epoch, an epoch is `max` over the stream
lengths, and the per-stream pass count is logged per step and printed in the
epoch line — so the ratio is on the page instead of in a comment that can
drift from it. Caught before stages 2-3 ever ran; no checkpoint carries it.

### What the head needed before any of this was worth doing

`fitness` is a **mean-pooled** scalar: one number per sequence from the mean
of the token representations. A one-nucleotide change in an 87 nt construct
moves that mean by about 1/87 of one token's delta. If that lands under the
head's own numerical noise then no amount of training can give it a fitness
landscape, and the failure would be silent in the worst way — the MSE would
fall, because predicting the mean of a zero-mean target is a good MSE, while
every Spearman it was scored on came back `NaN` and `np.nanmean` reported the
average of nothing.

Measured before the trainer was written: 16 variants of one wild type, one
substitution each, all distinct, separated by **4.8 x 10^5** times fp32
spacing at 3.34B tokens and 8.0 x 10^4 at random initialisation. The
architecture can represent the task. Pinned as `test_pharos.py` property 7d,
and the prediction spread is a logged column in the trainer for the same
reason — it is the one number that distinguishes a head learning slowly from
a head that has collapsed.

## Zero-shot fitness: PHAROS against the RNAGym leaderboard

PHAROS is a masked language model, so RNAGym's scoring convention -- the
masked-marginal log-likelihood ratio at the mutated positions -- needs no
fitness head, no fine-tuning and no training. It is stage 1's own masked
marginals read at the mutated positions, and it is directly comparable to the
published table. `eval_fitness_zeroshot.py` reproduces the convention from
RNAGym's baseline scripts rather than from its prose, because the two differ:
the code masks all of a variant's mutated positions *together* in the wild
type and sums the ratios, while the README describes masking them one at a
time.

The result, and the floor it has to clear, are below under finding 42. The
short version: **tenth of thirteen under the published convention, and below
a predictor that reads no sequence at all.** The first draft of this section
quoted the `wt-marginals` number -- a different strategy, on which PHAROS
leads the ribozyme and tRNA columns -- as though it were a leaderboard
position. It is not one, and that framing is corrected rather than kept.

### 42. The RNAGym ncRNA leaderboard is, to first order, a mutation counter

Every other head in this project is reported against a floor. Secondary
structure is quoted beside the majority-class rate, because dot-bracket is
mostly unpaired and an accuracy without that number is not a measurement. The
MLM is quoted beside the corpus unigram at 2.0165 bits. Accuracy is quoted
beside chance. The fitness Spearman had no such floor, and neither does the
published leaderboard.

So one was computed. **A predictor that reads no sequence, runs no model, and
knows only how many positions a variant changed** — the negative mutation
count:

| | ribozyme (26) | tRNA (3) | aptamer (2) | macro |
|---|---|---|---|---|
| Evo 2 (40B), rank 1 | 0.1081 | 0.4310 | 0.0970 | 0.2120 |
| RNA-ERNIE, rank 2 | 0.1343 | 0.4161 | 0.0306 | 0.1937 |
| Evo 2 (7B), rank 3 | 0.0651 | 0.3867 | 0.1192 | 0.1904 |
| **minus the mutation count** | **0.1947** | **0.4832** | −0.1173 | **0.1868** |
| AIDO.RNA (1.6B), rank 4 | 0.0740 | 0.3885 | 0.0847 | 0.1824 |

It places **fourth of thirteen, outranking 9 of the 12 published models**, and
it is ahead of **every published entry on both the ribozyme and the tRNA
column** — the two where the models are weakest. Only the aptamer column,
where it scores −0.1173, keeps it out of the top three. On
`Kobori_2015_ribozyme_p4` it reaches 0.670 and on `Li_2016_tRNA` 0.602; nine
of the 31 assays have |rho| above 0.3 from mutation count alone.

This does not make the benchmark worthless. More mutations *are* worse, a
likelihood-based score should capture that, and the aptamer column is where
the baseline fails and the models do not. But it does mean a leaderboard
position on these three columns is substantially a statement about how well a
score tracks mutation count, and that **9 of the 12 published entries do not
beat a predictor that reads nothing**. The three that do -- Evo 2 at 40B and
7B, and RNA-ERNIE -- are ahead on the macro by 0.025, 0.007 and 0.004, and
all three are behind it on two of the three categories.

`eval_fitness_zeroshot.py` now prints the baseline as a row in the table on
every run, with the count of assays it cannot rank (`Pitt_2010_ribozyme` is a
pure single-mutant scan, so mutation count cannot order it at all — recorded
as 0, not skipped, so the baseline and the model are averaged over the same
26 ribozymes rather than over 25 and 26 printed side by side).

### Zero-shot: what PHAROS actually scores, under both conventions

| strategy | ribozyme | tRNA | aptamer | macro | rank of 13 |
|---|---|---|---|---|---|
| `masked-marginals` (the published column) | −0.0061 | 0.2200 | 0.0602 | **0.0913** | 10 |
| `wt-marginals` | 0.1560 | 0.4407 | −0.0867 | 0.1700 | 5 |
| mutation count only | 0.1947 | 0.4832 | −0.1173 | 0.1868 | 4 |

**Under the convention the leaderboard is built from, PHAROS is tenth of
thirteen**, and both of its strategies are below the mutation-count floor.
The `wt-marginals` row leads the ribozyme and tRNA columns against every
published model, but `wt-marginals` is not what the published column is, and
quoting it as a leaderboard position would be wrong. Both are written to
`data/samples/analysis/fitness_zeroshot_*.json`, each labelled with its
strategy, and the pipeline runs both.

Three diagnostics were run before accepting the masked number, because an
85-point gap between two scoring conventions is the shape of a bug:

* **A span prior — refuted.** Stage 1 masks geometric spans of mean 3, and
  the benchmark masks isolated positions, so the model might simply be bad at
  filling scattered gaps. Measured on the same held-out sample at the same
  15% rate, changing only the shape: span 1.7817 bits, **scattered 1.7680**.
  The model is marginally *better* on the shape the benchmark uses.
* **Recycling depth — no effect.** 1.7954 / 1.7817 / 1.7790 bits at 1, 2 and
  3 loops on span masks. Two and three are within 0.003 of each other, so the
  scorer's `n_loops=3` is not costing anything.
* **Across-depth aggregation — not the cause.** A masked-marginal score is a
  sum over the mutated positions, so it could rank correctly inside a fixed
  mutation depth and misalign the depths against each other. It does not: the
  n-weighted within-depth Spearman matches the overall one almost exactly
  (`Zhang_2020_cpeb3` 0.1184 against 0.1116, `Roberts_2023_hp` 0.0132 against
  0.0133).

What is left is the model. At 3.34B tokens its masked marginals put 0.41
accuracy on a held-out base against a chance of 0.25 — informative, and not
yet confident enough for the log-likelihood ratio at a mutated position to
order a ribozyme library. The honest statement is that this is a checkpoint
41.8% of the way through stage 1 and the number is a baseline to improve, not
a result.

## Rechecking the pipeline: findings 43-45

Stage 6 landed, so the whole pipeline was walked again — every stage started,
every status file parsed, every metric asked the one question this audit keeps
asking: *is anything checking that this number is a number?*

### 43. The block scorer's micro-average recall has never executed, and could not

`train_block_scorer.py`'s `evaluate()` computes two recalls per level. The
chain-weighted macro, and a micro average whose twelve-line comment argues at
length that it is the only meaningful one:

> `np.mean` over per-chain recalls weights a 70-nucleotide tRNA with 11
> positive blocks the same as a 4,450-nucleotide rRNA with 833, and 93.6% of
> the test split is under 128 nt — where the 12% budget keeps about ONE block,
> so recall is capped near 0.1 whatever the scorer does. The macro average
> therefore reports the budget on short chains, not the model.

The commit that added it added the two `append` calls and **not the two
dictionary keys they append to**:

```python
acc = {f"{lvl}_{m}": [] for lvl in ("l1", "l2")
       for m in ("recall", "precision", "pos", "kept")}   # four keys
...
acc[f"{lvl}_recovered_total"].append(r * npos)            # KeyError, first chain
```

So `evaluate()` raises on its first chain, every mode, and the whole stage
cannot run. It has not run: `block_scorer_results.json` was written on
2026-09-21 and the micro average arrived afterwards, and the pipeline skips
the stage because `.done-scorer` is present. A hard crash has been sitting in
the curriculum, behind a done-marker, for two weeks.

The second half is what made it invisible. Three lines below, the consumer is
defensive:

```python
tot = sum(acc.get(f"{lvl}_pos_total", []))
res[f"{lvl}_recall_micro"] = round(rec / tot, 4) if tot else None
```

`.get(key, [])` turns a missing key into an empty list, an empty list into
`tot = 0`, and `tot = 0` into `None`. The saved report therefore reads
`l1_recall_micro: null` — which a reader parses as "not measured yet", not as
"cannot be measured". A guard written to survive missing data disguised a
crash as an absence.

Both halves fixed: the accumulator names every key it appends to, and the
consumer indexes rather than `.get`s, so a key that goes missing again fails
loudly. `test_head_metrics.py` now asserts the micro average is a number by
*running* `evaluate()` on the model-free `separation` mode — no GPU, no
checkpoint — because a source-level check for a missing key is a regex over
code, and the last two regex-over-code tests in this audit both got it wrong.

The learned scorer does beat its floors, on the split it was trained under:
L2 recall 0.8345 learned, 0.6333 separation prior, 0.5435 random, a sequence
gain of +0.2012. Those four modes are run and reported — the floor discipline
is present in this file, at the end of training. It is absent from the
per-epoch validation, which reports the learned recall alone.

**This connects to the standing WARN.** `verify_claims.py` reports that four
result files predate the 2026-09-24 split re-draw, and
`block_scorer_results.json` is one of them: its numbers are measured on a
split where 63.8% of today's test chains were in the train set. The obvious
remedy is to re-measure under the current corpus — and until this fix, that
was *impossible*, because `evaluate()` raised on its first chain in every
mode. The stage is re-runnable for the first time since the micro average
landed. Doing it costs a GPU and about thirty epochs, so it is a decision
rather than a fix, and `.done-scorer` is deliberately left in place.

### 44. The fitness scorer printed a partial load instead of refusing it

Mine, caught in review before it shipped a number.
`eval_fitness_zeroshot.py` loaded its checkpoint with `strict=False`, printed
the count of missing keys, and scored the model anyway. A `--size` that did
not match the checkpoint, a renamed trunk parameter or a half-written file
would have scored a partly random model and printed it a position on a
published leaderboard.

`eval_mlm_checkpoint.py` has had `_check_load` for exactly this since the
09-25 audit — it tolerates the heads that post-date a run, names anything
else, and raises rather than score trunk weight that is missing. The fitness
scorer now calls that function rather than its own weaker version, so the two
cannot drift about what counts as a tolerable absence.

### 45. A zero correlation does not say which kind of zero it is

`_regression_metrics` in stage 5 returns `r = 0.0` when the denominator
vanishes — which is what a *collapsed* head produces — and `r ≈ 0.0` is also
what a live, freely varying, uncorrelated head produces. In the per-step time
series the two were the same number. `evaluate()`'s pooled `rigidity_r_pooled`
already returns `None` rather than `0` in that situation; the per-step metric,
which is what the csv curve is made of, did not.

It now returns `{tag}_pred_sd` beside `{tag}_r`, and `_stage5_fields()` grows
the csv automatically, so `part_rigidity_pred_sd` and `part_fluct_pred_sd` are
columns. Stage 6 carries the same number for the same reason, with a
threshold rather than an equality — **`torch.std` of a constant tensor returns
2.98e-08, not zero**, because the two-pass variance does not cancel in fp32,
so `== 0` would never fire. `DEAD_PRED_SD` is 1e-5: two orders above float
noise and two orders below the 0.0024 a live-but-untrained head was measured
at after 250 steps. The first value tried was 1e-3, which sits a factor of two
under a live head and would have fired on an ordinary first epoch — which is
how a guard gets switched off.

### Also fixed, found by a test that already existed

`test_head_metrics.py` asserts that every key of a trainer's epoch history is
a declared csv column — an invariant that exists because stage 5 once declared
nine columns and passed forty. Stage 6's two per-assay breakdowns are lists
and were put in the history and then filtered out at the `runlog.log` call,
which satisfied the csv and broke the invariant. They live beside the history
now and reach the results json by their own route. The check caught it on the
first run after it was written.

### 46. The NaN guard crashed stage 5 on its first optimiser step

Finding 34 added `check_loss` to all four trainers so a non-finite loss could
not reach the optimiser. In `train_pharos.py` it was written

```python
check_loss(loss, gstep, parts)
```

and stage 5 has no `gstep`. Its counter is `step`, restored from the resume
record 50 lines above. So the call raised `NameError` on the **first
optimiser step of the stage**, every time, and the guard added to prevent a
silent failure was itself a hard one.

Nothing reported it for two weeks because nothing ran it. Stage 5 has never
executed — `.done-stage5` has never existed — and the three checks that could
have caught it all stop short: `--help` exits before the loop,
`test_head_metrics.py` imports the module and calls its metric helpers but not
its training loop, and the unit suites never construct the optimiser. The
`--smoke` flag exists precisely for this and had not been run since the guard
landed.

Fixed, and generalised. `test_head_metrics.py` now runs a static
undefined-name pass over `scripts`, `src` and `research` — the whole class, in
about a second, in a suite the pipeline gate runs. It reports clean.

### 47. The verification gate could not be parsed by the Python the project declares

The same pass, run at the floor of `requires-python` rather than at the
interpreter in the venv, found two modules that are SyntaxErrors below Python
3.12: a backslash inside an f-string expression is PEP 701, which landed in

One of the two was `scripts/sampling/verify_claims.py` — **the gate that
decides whether training may proceed**. On the minimum Python this project
says it supports, the thing that checks everything else does not start.

Both rewritten to hold the literal in a variable, so the declared range is now
true rather than aspirational, and the parse check runs at whatever
`requires-python` says rather than at whatever happens to be installed. A
floor that is only ever tested on one interpreter above it is not a floor.

### 48. Four test modules existed, passed, and were never run by the gate

`verify_claims.py` ran 17 of the 21 `test_*.py` modules in the tree. The four
it did not run were `test_head_metrics.py`, `test_residue_guard_bias.py`,
`eval/test_metrics.py` and `test_shared_moe.py`.

Three of the four are now gated. The fourth was not a test:
`test_residue_guard_bias.py` asserts nothing, reports no pass or fail, and
exits 0 whatever it finds — it recomputes an analysis over 8,043 gzipped
structures, which takes fifteen minutes. Gating it would have added a quarter
of an hour to a check that fires every thirty minutes and could not have
caught anything. It is renamed `measure_residue_guard_bias.py`, which is what
the rest of `scripts/sampling/` calls a script of that kind, so the
"every `test_*.py` is gated" invariant is true rather than satisfied by
padding. A file has to be what its name says — the same principle as finding
39, where a column named `DMS_score` turned out to be sequencing read
counts.

The first of those is the test **of the floors** — the AUROC that must be 0.5
for a constant score, the correlation that must be 0 for a constant
prediction, the class lift that must be 0 for a head that has learned only
the prior. It is the test that every other head's number is judged against,
and it caught two live defects the first time it was run after stage 6
landed: findings 45 and the history-vs-csv drift below.

All 21 are gated now, and the gate asserts it covers the directory rather
than trusting a hand-maintained list: a new `test_*.py` that is not in the
list fails verification. A list of checks that drifts from the checks that
exist fails silently in the only direction that matters — a suite nobody runs
reports nothing, so the gate stays green.

### 49. Two of the four trainers had no way to check that they start

Findings 43 and 46 are the same shape: a hard crash sitting in a stage that
had not been run, behind a done-marker in one case and an empty done-marker
in the other. What let both hide for two weeks is that the cheap check does
not exist for every stage.

Stage 5 and stages 2-3/6 each carry `--smoke N --device cpu`: run N steps,
exercise the epoch-end evaluation, write no checkpoint. Finding 46 was found
by running it. `train_block_scorer.py` had no such escape — it is GPU-only by
design, and the docstring's reason is sound for *the four ablation passes
that give the result its meaning* and has nothing to say about *does the loop
start*. So the only way to find out was a free A100, and the KeyError in its
`evaluate()` waited instead.

It has the same escape now, including the evaluation on both the model-free
and the learned mode, and it **fails** rather than passes if the micro
average comes back `None` — which is what a missing accumulator key looks
like from outside. `train(args)` returns an int and `main()` propagates it,
because a smoke test whose failure does not set the exit code is a smoke test
the cron runner reads as a pass.

`pretrain_mlm.py` still has none. It is the one stage with 25,200 production
steps behind it, so "does it start" is answered by the run; its `check_loss`
call was checked by reading (`seen = step = resumed_padded = 0`,
unconditional, 334 lines above the call) and by the new static pass.

## Reading the architecture: findings 50-52

A line-by-line read of the trunk, the mixers, both MoE flavours and the model
assembly — the files the audit had so far trusted because their tests pass.

### 50. The MoE balance loss moved with how padded the batch was

`SharedMoEFeedForward` is the feed-forward of the model that is actually
training. Its Switch-form auxiliary is `E * sum_i(frac_i * pbar_i)`, which has
a floor of **1.0 at perfect uniformity** — the value `pretrain_mlm.py` states
in its own comment and the value the monitor's "0.18 floor" (0.01 × 18 blocks)
is computed from. That floor holds only if `sum_i frac_i` is exactly 1, and
that requires the numerator and the normaliser to be taken over the same
tokens. They were not:

```python
frac = (fired * mf.unsqueeze(-1)).sum(0) / (n_tok * width.mean().clamp(min=1.0))
#            ^^ masked, real tokens only        ^^ UNMASKED, padding included
```

Four lines below, in the same returned dict, `mean_width` is computed
*masked*. So the width that was reported and the width that entered the
gradient were two different numbers, in the same function.

`MoEFeedForward` — the fixed-top-k version this was derived from — divides by
the exact constant `top_k` and cannot have the problem. Variable-width nucleus
routing turned that constant into a quantity, and the quantity was measured
over the wrong set.

**Measured on shared400 at 3.34B tokens**, a 4×128 batch with 20.3% padding:
masked mean width 3.663, unmasked 3.526, and the per-block ratio ran from
**0.766 to 1.215 across the eighteen blocks of a single forward pass**. The
floor was therefore not 1.0 but `masked_mean_width / all_rows_mean_width`,
which varies per block, per batch, with the padding fraction and with how the
padding happened to route. The auxiliary's effective weight was a function of
batch composition.

Fixed by computing the masked mean once and using it for both, so the number
in the gradient and the number in the log are the same tensor. Verified: the
balance term now sits at 1.000–1.006 at initialisation from 0% to 80%
padding, a spread of 0.005, where the quantity it replaced drifted by a
factor of 1.6 between blocks. `test_shared_moe.py` pins it.

### 51. §6.2's physics coupling has no caller

`TokenTrunk.forward` takes a `pair_bias_fn`. **Nothing passes one.**
`Pharos.forward` calls `self.trunk(x, mask, feats, n_loops=..., supervise=...)`
and no other caller exists, so `FullAttention` always receives
`pair_bias=None`, the branch that adds the bias never runs, and
`ElectrostaticBias` — constructed as `self.elec` in `Pharos.__init__` — is
**never called from anywhere in the repository**.

Three docstrings asserted the opposite, in the present tense:

* `trunk.py`: "Physics and refinement are coupled, not sequential … a change
  in ionic condition changes what attends to what on the next loop"
* `attention.py`: "The bias is where the Hamiltonian reaches the token track
  … so the ionic condition changes what attends to what rather than only
  re-scoring the output"
* `pharos.py`: "That is the mechanism by which an ionic condition changes a
  prediction, so it is computed from `physics.manning`, not learned"

It is **computed from nothing, because it is not computed**. 25 parameters
(`elec.log_scale`, and `bias_scale` on the two full-attention blocks) receive
no gradient.

This is not a loose wire. It is orphaned by the §9 change that made head 3 a
diffusion decoder: the bias needs the previous loop's *distance estimate*, and
a denoiser emits no coordinates in a forward pass, so there is nothing to feed
it. `Pharos.forward` also takes no ionic condition, which is the second sign
it was never plumbed. Wiring it means running the pair track inside the trunk
loop — 21M pairs at L=4,608, every loop — so it is a costed architecture
decision, not a patch.

Declared rather than faked. `pharos.UNWIRED` names it with the reason, in the
shape property 7c uses for the heads, and new property **7e** asserts the
declaration is *true*: if anyone wires it the test fails and the entry must be
removed, so the declaration cannot go stale the way the three docstrings did.
An output nothing reads and a module nothing calls are the same defect; the
heads got a pinned declaration in the 09-26 audit and the modules did not.

### 52. The public `forward` built every pair from sequence 0

```python
pair = self.pair_proj(torch.cat([h[0, ii], h[0, jj]], dim=-1))
```

On a batch of more than one, every pair was built from the first sequence's
hidden states and returned a correctly-shaped answer about the wrong chain.

Nothing in training hit it: `train_pharos.py` builds its own pairs with a real
per-chain `bidx`, because it needs one index set per chain and the
coevolution injection. So there were two implementations of one thing, the
trainer's was correct, and **the broken one was the model's public
interface** — the same shape as the deleted `PharosHeads.loss` in finding 36.

Its only caller was `test_pharos.py` property 6, running a batch of 2 and
asserting the output's *shape*, which was right.

`pair_index` now accepts `(bb, ii, jj)` and refuses a bare `(ii, jj)` on a
batch of more than one rather than silently picking sequence 0. Property 6
passes the batch index and checks that the same `(i, j)` on two different
sequences gives two different answers — a value check where there was a shape
check.

### 53. Padding changed the fluctuation at real positions

`StiffnessField.forward(tok, mask)` **took the mask and never used it.**

That looks harmless — the diagonal stiffness blocks are a local function of
two adjacent residues, so they were always clean. But the amplitudes come from
`block_tridiagonal_variance`, a sequential forward-**backward** recursion, and
the backward sweep starts at the LAST step and carries inwards. Whatever the
padded region computed therefore reached the real positions:

    fluctuation, max delta at REAL positions when only the padding changed
      before:  2.062e-01
      after:   0.000e+00   (three shapes, exactly zero)

`fluctuation` is a stage-5 supervision target (`part_fluctuation`,
`fluct_r`, `fluct_base`). Stage 5 has not run, so no checkpoint carries it.

The fix decouples rather than zeroes: an unreal step's diagonal block becomes
the identity — well-conditioned, so the recursion's solves cannot meet a
singular block — and `Fo[i]` is zeroed whenever step `i` or `i+1` is unreal,
which makes `C = 0`, makes the Schur correction exactly zero, and cuts the
chain at the boundary.

**`test_pharos.py` property 5 is "padding cannot change a real position" and
it did not catch this**, because it checked `hidden` — the trunk's output —
and the leak was downstream of it. It now checks `fluctuation`,
`disorder_logit` and `stiffness_diag` as well. A property worth stating about
one output is worth stating about all of them.

The 09-26 audit found two live head-numbering schemes, corrected the trainers,

They did not. `heads.py` — **the file that defines `HEAD_SPEC`** — still

|---|---|---|
| 5 | Mg2+ sites | reactivity |
| 6 | rigidity | mg_sites |
| 7 | reactivity | rigidity |
| 8 | fitness | disorder |
| 9 | splicing | geometry |
| 10 | base identity | motif |

plus `# 5` on `mg_site`, `# 6` on `rigidity`, `# 7` on reactivity, `# 8` on

### 55. The token budget did not bind: 71% of batches exceeded it

`Pharos3DDataset.length_batches` sizes a batch as `(n+1) * longest`, because
every chain pads to the longest. Its own comment says exactly that. The code
compared against `self.meta[cur[0]]["length"]` — the **first** chain in the
batch — and the bucket is shuffled, so every chain between the first and the
longest was invisible to the estimate.

Measured on the training split:

| budget | batches | worst actual cost | over budget |
|---|---|---|---|
| 16,384 | 73 | 20,125 (**1.23×**) | 49 (**67.1%**) |
| 32,768 | 38 | 37,510 (1.14×) | 27 (**71.1%**) |

It was never unbounded — the geometric buckets cap the ratio at 1.5 — but a
declared limit exceeded by two batches in three is an advisory, and this
particular limit is what `gpu_cron_runner.sh` sizes VRAM against. Stage 5's
OOM handler skips a batch that does not fit, so a budget that does not bind
makes the skipped set length-correlated, which makes the training
distribution length-correlated, silently.

One line: track the running maximum. After it, **0 batches exceed at any
budget**, worst cost exactly 1.00×, at a cost of 4% more batches.
`test_dataset.py` property 10 pins it across two splits and three budgets.

Found by reading the comment against the code — the comment was right and the
code was not, which is the reverse of findings 41 and 51 and just as hard to
see.

Also in `loader.py`: `prewarm` divided `ru_maxrss` by 1e6 and called the
result GiB. `ru_maxrss` is in kilobytes on Linux, so that is GB — a 7.4%
overstatement, printed next to a VRAM budget.

### Observation, not a finding: the violation term is a high-sigma penalty

`DiffusionStructureHead.loss` adds `violation_weight * violation` **outside**
the EDM sigma-weighting, where `violation` is measured on the denoised
prediction at a randomly sampled sigma. At low sigma the prediction is close
to the true structure and the term is near zero; at high sigma it is near the
mean structure and the term is large. So the bond penalty is almost entirely
a high-noise penalty, while the geometry that reaches a sampled structure is
set by the low-sigma steps.

That is defensible — an x0-prediction should be a plausible structure at any
noise level — and it is not obviously wrong, so it is recorded rather than
changed. It is worth one A/B once stage 5 runs: sigma-weighting the violation
the way `se` is weighted, against the current form.

### 56. The fluctuation head was trained on a target that moved with the batch

```python
l2 = F.smooth_l1_loss(fl, (t["b_factor_z"][rm].float()
                           - t["b_factor_z"][rm].float().min()).clamp(min=0))
```

`fluctuation` is an amplitude, so its target has to be non-negative, and the
shift that makes it so is **the minimum over the current batch**. The same
residue therefore gets a different target depending on which other chains
share its batch.

Measured over 35 stage-5 batches at a 16k budget: the offset ran from
**−1.225 to −6.051**, a spread of **4.83** — against a signal whose standard
deviation is 1.0, because `b_factor_z` is z-scored per chain. The head is
asked to predict a quantity that moves by five standard deviations for
reasons that have nothing to do with the residue.

It is invisible in the metric reported beside it. `_regression_metrics`
returns Pearson `fluct_r`, and **Pearson is invariant to a constant offset**,
so the correlation reads clean while the loss cannot converge below the
variance of the offset. The one number that would have shown it,
`fluct_base` — the constant-predictor loss — moves with the batch too, so the
loss and its floor drift together and the ratio looks stable.

`rigidity`, the head immediately above it, uses the raw `b_factor_z` and is
batch-independent. The two targets are three lines apart.

Stage 5 has never run, so nothing carries it.

### 57. Muon orthogonalised across the expert axis, not within each expert

```python
flat = upd.reshape(upd.size(0), -1)      # (E, d, f) -> (E, d*f)
flat = newton_schulz(flat, group["ns_steps"])
```

`GroupedExperts.w1` is `(32, 512, 512)` — **thirty-two matrices**, not one.
Flattening to `(E, d*f)` and orthogonalising makes the *experts mutually
orthogonal* instead of making each expert's weight matrix orthogonal, which
is a different operation and not the one Muon's spectral argument licenses.
Measured: after flattening, slice 0's singular values span [0.022, 0.170] —
the slice is not orthogonal at all.

`max(1.0, p.size(0) / p.size(-1))`, the shape-parity scale, had the same
error: for `(E, d, f)` it computed `E/f` rather than `d/f`.

Every independent-expert config hits it — mini, small and base400, which is
32 of their 212 Muon tensors. **shared400, which stage 1 actually runs, has
only 2-D tensors in Muon and is unaffected**, so nothing in flight carries
it. The historical Muon-vs-AdamW A/B that chose this optimizer was
"reproduced independently on a second model"; if that model was `small`, half
of that evidence was measuring a mis-applied update.

`newton_schulz` now takes the last two dimensions as the matrix and anything
in front as a batch, with **per-slice** normalisation — a single Frobenius
norm over a stack would let one expert's gradient scale set every other
expert's step. The 2-D path is bit-identical: batched and slice-by-slice
agree to 0.00e+00, and for a 2-D input the new normalisation, transpose and
scale all reduce to exactly the old expressions.

### 58. "Singular values into [0.7, 1.3]" is true for 69% of the tensors

The same read found the coefficient comment asserting the iteration "is tuned
to drive singular values into [~0.7, ~1.3] in five steps". Measured:

| input | condition number | after NS5 | |
|---|---|---|---|
| (768, 2304) | 3.7 | **[0.681, 1.140]** | as claimed |
| (2304, 768) | 3.7 | [0.680, 1.139] | as claimed |
| (512, 512) | 1,723 | [0.024, 1.204] | **not** |
| (768, 768) | 5,458 | [0.012, 1.204] | **not** |

A square random Gaussian has its smallest singular value at the
Marchenko-Pastur edge, near zero, and five steps cannot lift it. The
compression is still large — 5,458 to 105, a 52× improvement — and the upper
bound always holds, which is what stops the update exploding. The lower one
does not.

**31% of shared400's 222 Muon tensors are square**, holding 39.5M of its
343M Muon parameters, so this is not a corner case for the model in flight.
It is a property of the iteration rather than a bug — the reference Muon
behaves the same — and the correction is to the claim, not the code: five
more matmuls per tensor per step is a real cost and changing it mid-run would
change what is training.

### And Muon had no test module at all

The optimizer owns 343M of shared400's parameters, was chosen over AdamW on a
measured A/B, and `verify_claims.py` gated twenty test modules of which none
touched it. Findings 57 and 58 both came out of writing the first one.
`src/pharos/train/test_muon.py` pins orthogonality on well-conditioned input,
spectral compression on ill-conditioned input, scale invariance (which is why
this file's non-standard momentum accumulation — `buf = m*buf + g` rather
than `m*buf + (1-m)*g` — is immaterial rather than a 20× rate error at
momentum 0.95), per-slice behaviour on stacks, that a step descends on both
a 2-D and a 3-D parameter, and that the Muon/AdamW split is a partition of
the trainable parameters with no embedding on the Muon side.

### Open question, not a finding: are production gradients orthogonalisable?

Finding 58 established that five Newton-Schulz steps reach [0.7, 1.3] for a
well-conditioned matrix and not for a near-singular one. The obvious follow-up
is whether REAL gradients are the first kind or the second, and it is not
settled.

A first probe reported "0 of 168 real gradients land in [0.6, 1.4]". **That
number is an artifact of the probe and is withdrawn.** It used a 2x64 = 128
token batch, and a gradient of a `(d_out, d_in)` weight from N tokens has rank
at most N — against matrices up to 2,304 wide, so the singular values were
zero for arithmetic reasons and said nothing about the optimizer.

Repeated at 3,840 tokens, which exceeds every matrix dimension:

```
square      n= 66  full-rank  0/66   output sigma_min median 0.0000
non-square  n=138  full-rank 37/138  output sigma_min median 0.0006
2 of 204 real gradients land in [0.6, 1.4] after NS5
```

Still mostly rank-deficient, and still not conclusive: production runs
**180,224 tokens a step**, 47x this probe and 78x the widest matrix, and
rank-deficiency at 3,840 tokens may simply not survive that. Settling it needs
a production-scale batch, which needs the GPU.

One part of it is already settled and is not a batch-size question.
`trunk.blocks.0.mixer.a.weight` is the GDN forget gate, `(12, 768)` — it needs
twelve tokens to be full rank and had 3,840 — and its gradient came back
**rank 2 of 12**. For the small per-head gate matrices the gradient is
genuinely low-rank, so Newton-Schulz is amplifying two directions to unit norm
and leaving ten at zero. Whether that is a problem or exactly what one wants
from Muon is an open question; what is certain is that "the update moves every
direction equally" is not what happens to those tensors.

Recorded here rather than acted on. The claim in `muon.py` has been corrected
to what is measured; the behaviour has not been changed, because changing
`ns_steps` costs five matmuls per tensor per step and would change what is
training on the strength of an inconclusive measurement.
