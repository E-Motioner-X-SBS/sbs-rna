# Audit, 2026-09-26

Same hunt, same class: **a component that exists, is measured, and whose output
is never checked for basic validity.** Sixteen findings, all in the
monitoring and supervision layer rather than the model. Two of them are the same literal
string, `pretrain_small.pt`, written into two files and stale in both from the
moment the run moved to `shared400` — and in each file a different guard
turned the staleness into silence rather than an error. Everything below is pinned in
`scripts/sampling/verify_claims.py` or in `src/pharos/data/test_dataset.py`.

Training was stopped at step 13,750 on 2026-09-25 and the scheduler is held, so
none of this was found by watching a run. It was found by asking, of each
number that gets quoted, *where does this come from and when was it last
actually computed.*

### Why 20 matters beyond the count

Head 9, one block above it in the same function, gets this right: *"Unannotated
pairs are excluded by the mask rather than given a class: not-a-base-pair is
not a kind of base pair."* Head 10 is the same sentence about loops, and it was
never written. The consequence is directional, not just noisy — class 0 is the
majority class, so the unfounded labels all push the same way:

| | class 0 (no loop) | class 1 (hairpin) | class 2 (internal) |
|---|---|---|---|
| as trained | **74.4%** | 7.3% | 18.3% |
| on chains where the label means something | **64.4%** | 10.1% | 25.5% |

74.4% was also head 10's reported majority baseline, so a head that learned
nothing but "predict 0" was being scored against a bar that 28.2% of its own
training data had raised for it. Measured through the real batch path after the
fix: `loop_mask` covers 82.9% of residues instead of 100%, and the class shares
land at 63.7 / 10.3 / 25.9.

`shared400` at step 13,750 (2.069B tokens, 512 experts, fp32 on cpu),
against `log 512 = 6.238` nats:

|---|---|---|---|
| per-token routing entropy | **0.341 nats** | 6.238 | **5.5% of uniform** |

Not collapsed — the opposite, and by a wide margin. The 32-expert predecessor

### The telemetry defect is now impossible to repeat quietly

`csv.DictWriter(extrasaction="ignore")` is the right behaviour for a writer —
a stray key must not kill a training run at hour nine — and the wrong
behaviour for a codebase, because the caller's author gets no signal. Both
instances of this defect were found by reading a csv header, which is not a
method that scales. `RunLog.log` now prints one line per undeclared key per
run:

```
[telemetry] stage5_3d: 31 column(s) passed to log() but not declared,
so they are NOT being written: part_balance, part_base, ...
```

It still writes the row. It just stops being silent about what it left out.

### The worst one, and the two fixes that caught it

Finding 32 is the only one today where a wrong number was actually produced,
written to disk, and would have been quoted. It is also the clearest case of
the pattern, because every individual piece was correct:

- redrawing the split family-disjoint was a deliberate improvement;
- `Pharos3DDataset(DATA, split="test")` does exactly what it says;
- `measure_cascade_recall.py` loads the scorer and measures recall correctly;
- the scheduler re-runs it every 24 hours, as intended.

What was missing is that a model and an evaluation have to agree on *which
draw of the split they mean*, and nothing recorded it on either side. So the
composition of the answer was wrong while every part of it was right.

Two of today's earlier fixes are what surfaced it. Finding 19 made a failing
GPU task raise a problem instead of printing `FAILED` into a log, and finding
22 made the watcher report what it is actually looking at — which is how a
cron tick at 23:34 came to leave evidence worth reading at all. The guard now
composes the other way too: the re-measurement exits 1, and that exit is now
visible instead of swallowed.

Note what the numbers would have looked like. Contamination inflates; the new
test split is 94% short chains and cascade recall is strongly length-dependent,
which deflates. The aggregate moved 0.264 → 0.2115 — *down*, in the direction
that reads as an honest regression. A plausible number moving the plausible way
is what makes this class of defect expensive.

**And it is not one file.** Every pinned model result in the repository was
measured under the old draw, because the re-draw postdates every checkpoint:

| result file | its test split | corpus now |
|---|---|---|
| `block_scorer_results.json` | 1,450 | 4,081 |
| `block_scorer_results_small.json` | 1,450 | 4,081 |
| `pharos_small_results.json` | 1,358 | 3,993 after stage-5 filters |
| `pharos_small_results_randinit.json` | 1,358 | 3,993 |

Those numbers are **valid for the split they were measured on** and are not
being retracted. What is now recorded, rather than assumed, is that they are
not measurements of the current corpus, and that re-measuring any of them
requires retraining the model under this draw — scoring the existing
checkpoints on today's test set is the contamination above, not an update.
`verify_claims.py` prints the inventory as a warning every run.

### The scheduler was suppressing itself

Finding 31 is the one with teeth, because it is the only one that could have
stopped training rather than merely mis-described it. `do_gpu_work` starts
nothing when `training_alive()` is true, and `training_alive()` was true
whenever any process on the machine had a trainer's file name in its command
line. The watcher runs `verify_claims.py` at the top of every tick, and
`verify_claims.py` runs `--help` on all six trainers. The window is short and
the tick is 30 minutes, so this would have fired occasionally, skipped a
resume, and left behind one line in a log saying training was already running.

It is checked behaviourally now rather than by reading the source: the guard
starts a process whose argv contains `scripts/train_pharos.py`, confirms the
old predicate matches it, and requires the new one not to.

### The one that is still live

Finding 27 is not a defect that has already fired — it is one that is about to.
`mars_to_parquet.py` is running now with a four-hour timeout. When it finishes,
the held-out digest moves off `7c207664`, and the next reading of the curve
will not belong to the seven readings already in the file. That is now
**stated** in three places rather than discovered later:

- the trainer prints `held-out shard set unchanged (7c207664)` on resume, or a
  four-line warning if it has moved;
- the evaluation csv carries the digest per row, so two numbers are known to
  be comparable or known not to be;
- `verify_claims.py` fails if one csv splices two digests, and warns when the
  corpus has grown past the recorded one.

What it does **not** do is pick for you. Freezing the reserved set would keep
the curve comparable and let the held-out shards fall behind the corpus;
letting it move keeps the evaluation representative and restarts the curve.
That is a judgement about what the number is for, and it is recorded here
rather than decided quietly in a sort order.

## Finding 33 — coordinates stored as float16 in the raw crystal frame

Asked a plain question of the corpus -- do we have backbone information --
and the answer is yes, with one defect in how it is stored.

`pharos3d` carries `coords (N, 3, 3) float16` and `coord_mask (N, 3) bool`:
phosphate, C4', glycosidic nitrogen, per residue, over 13,172,991 residues in
16,604 chains. Coverage is 99.94% / 99.55% / 99.33% and 16,602 of 16,604
chains carry some coordinate. The geometry is right: C4'-N measures a median
**3.378 A** against the reference 3.38, P-P **5.884** against 6.01, C4'-C4'
**6.132** against 6.0.

What nothing checked is the **frame** those floats are written in. They are
the deposition's own coordinates, uncentred, so the median |coord| is
**170 A** and the maximum **1310 A**. float16 spacing is not uniform: it is
0.0312 A at 32 A, 0.125 A at 128 A, 0.25 A at 256 A, 1.0 A at 1024. 71% of
stored coordinates sit beyond 128 A and 22% beyond 256 A, so most of this
corpus is quantised more coarsely than the precision the numbers imply.

The damage is measurable without the original float32, because C4'-N is a
near-rigid bond whose spread is almost pure noise. Binned by |coord|, robust
sd of that bond:

| \|coord\| (A) | n | median | robust sd | fp16 spacing |
|---|---|---|---|---|
| 0-32 | 70,064 | 3.379 | 0.0790 | 0.0010 |
| 32-64 | 310,236 | 3.375 | 0.0729 | 0.0312 |
| 64-128 | 1,080,503 | 3.376 | 0.0696 | 0.0625 |
| 128-256 | 1,842,261 | 3.380 | 0.0792 | 0.1250 |
| 256-512 | 628,302 | 3.387 | **0.1148** | 0.2500 |
| 512-2048 | 36,247 | 3.391 | **0.1636** | 0.5000 |

Flat at ~0.07 A -- real crystallographic variation -- until the fp16 spacing
overtakes it, then it doubles. That is the quantisation, visible directly.

**Why it survived.** Every check that could have caught it is translation
invariant. `DiffusionStructureHead.loss` centres through `random_rigid`, so
training never sees the offset; the bond-violation term reads differences,
which are unaffected by where the origin is; and the medians above are
correct precisely because quantisation is unbiased. The corpus looks healthy
from every angle except the one nobody took, which is the class this audit
keeps finding: measured, plausible, never checked for the thing that was
actually wrong.

**Cost and fix.** It is label noise on head 3's only supervision, ~0.10-0.16 A
where good backbone prediction is a 1-2 A problem. Centring each chain before
the float16 cast drops max |coord| from 1310 A to 169 and the median from 170
to 49, putting the whole corpus at <=0.125 A spacing and most of it at 0.031.
Centring at load time cannot recover it -- the precision is gone at write.
The structure head is translation invariant anyway, so nothing downstream
depends on the absolute frame being kept.

**Fixed, and the corpus rebuilt.** Centring happens in `build_entry` before
the float16 cast, over **resolved atoms only** -- the first version of the
measurement averaged the unresolved (0, 0, 0) slots in too, which dragged the
centroid tens of Angstroms off the chain and made centring look *worse* than
leaving it alone (0.1143 against 0.1044). That near-miss is worth keeping:
the fix had a bug that the fix's own metric reported as a negative result.

Corpus-wide, over all 13,172,991 residues:

| | max \|coord\| | median \|coord\| | C4'-N spread |
|---|---|---|---|
| before | 1310.0 A | 236.1 A | 0.0853 A |
| after | 202.0 A | 50.0 A | **0.0556 A** |

float32, the parser's own precision, gives 0.0511. No residue is left beyond
256 A. The bond median also moved 3.3866 -> 3.3819 against a 3.38 reference:
quantisation at that magnitude was biasing the bond, not just broadening it.

`coord_center` (float32, per chain) is written to every shard and into the
manifest, so `coords + coord_center` is the deposition frame again --
round-trip verified at 0.0312 A, half a float16 ULP.

**The split is bit-identical**: digest `3900e076` before and after, 16,604
chains, 13,172,991 residues, 63,298,800 contacts all unchanged. Nothing
measured against this corpus needs re-measuring; only the coordinates moved.
The old one is kept as `pharos3d_v3_uncentred`.

Two checks now exist where none did. `build_dataset.py` reads its own shards
back and refuses to ship a corpus whose max |coord| exceeds 256 A, whose
glycosidic bond is off reference, or whose bond spread exceeds 0.075 A, and
pins the numbers in `manifest["geometry"]`. `test_dataset.py` property 9
asserts the same three things plus the presence of `coord_center`; it fails
on the old corpus, which is the only evidence that it tests anything.

## Checked and not a defect: the b_factor_z tail

Asking the same question of the corpus' other float16 arrays -- is the
magnitude small enough that relative precision still holds -- turned up
`b_factor_z` spanning [-105.9, +105.9]. A z-score of 106 is not a z-score.

It is a thin tail: p99 is 3.59 and p99.9 is 6.49, and only 77 of 15,852

## Findings 34-37 — a full re-audit of the architecture

All sixteen test modules passed before this pass and all seventeen pass
after, `verify_claims.py` reproduces every claim, and `audit_head_outputs.py`
flags nothing. That is the point: four of these were live the whole time.

### 34. Nothing stopped a NaN

No trainer checked whether its loss was finite. `nan.backward()` runs,
`clip_grad_norm_` passes NaN through, `opt.step()` writes NaN into every
weight, the checkpoint at the next `ckpt_every` boundary saves it, and the
run continues for days producing a file that cannot be resumed from.

The held-out monitor could not see it either, and this is the sharper half.
`float("nan")` parses without complaint, and **every comparison against NaN
is False** -- so `bits >= UNIGRAM_BITS` was False, the reading was taken as
better than unigram, the no-progress check compared NaN deltas (also False),
and the verdict was **OK**. The monitor whose entire job is to notice a run
going wrong was structurally unable to notice the most obvious way one does.

Fixed both ends. `pharos.train.guard.check_loss` raises before the optimiser
and names which head went non-finite first, because the heads are summed and
the sum only records that something broke; all four trainers call it. The
monitor's `f()` now rejects non-finite as unreadable, which routes a NaN to
the existing ALERT. `src/pharos/train/test_guard.py` pins both, including
that the guard is called *before* `backward()` and not after.

| output | state |
|---|---|
| `disorder_logit` | label in every shard, named in stage 5's docstring as a head it trains, no loss term |
| `fitness` | `STAGE_WEIGHTS["fitness"] = 0.3` printed at startup and written into two report files, no loss term, 126 MB of NABench/RNAGym on disk |
| `splice_logits` | no corpus acquired |
| `ensemble_state_logits` | no observable distinguishes the states |

`disorder_logit` is the one worth dwelling on: the data was extracted,
shipped in every shard as `unobserved_seq_id`, documented, and the docstring
of the stage that was supposed to use it says it does. It cannot, as the
corpus stands -- the label names polymer positions that were never modelled
and the tokens are the modelled residues only, so a target aligned to them is
vacuously zero, which `mmcif_entities.residue_labels` states in as many

The phantom `fitness` weight is removed, the docstrings now say which heads
are and are not trained, and `test_pharos.py` property 7c pins the whole
emitted surface as three explicit sets -- 11 trained, 3 trained indirectly,
4 untrained with a stated reason each. A new head fails that test until
someone classifies it.

The first version of 7c discovered the sets by searching the trainers for
`out["key"]` and reported `fitness` as trained -- because the comment saying
there is no `out["fitness"]` anywhere contains the string `out["fitness"]`.
A check that greps its own prose, committed inside the thing built to catch
checks that cannot see. It is now a pinned list.

### 36. `PharosHeads.loss` was dead code that disagreed with the trainers

A static method summing every head under a documented weight table --
contact 1.0, distance 1.0, ss 0.5, mg 0.3, rigidity 0.3, reactivity 0.5,
base 0.2, fitness 0.5, splice 0.5, coords 1.0. **Called by nothing**: not the
trainers, not a test. The real stage-5 weights are assembled inline and are
not those; `distance` is 0.5 in the trainer against 1.0 here, and this table
is the one a reader finds first.

It also held the project's only non-finite guard, on a path no gradient ever
took, while the four trainers that do take gradients had none -- finding 34.
Deleted rather than wired up: two loss definitions is how they drift, this

### Also fixed: the monitor alarmed at its own pause

machine off is one people learn to ignore, which is the only way a monitor
fails. Both checks are now pause-aware; a held run reports 0 ALERT.
